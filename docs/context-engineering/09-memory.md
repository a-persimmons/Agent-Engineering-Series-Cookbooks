# 09｜Long-term Memory：哪些信息值得跨任务留下来

Long-term Memory 的第一道问题不是“存到哪里”，而是：

> 这条信息值得未来再次出现吗？

这一章只讨论 **Memory 作为一种 Context Source**。写入、检索、更新和遗忘的完整机制留到第 17 章。

![History、Task State 与 Long-term Memory 的分工](/diagrams/context/history-state-memory.svg)

## 什么更像长期记忆

### 稳定事实

例如用户长期偏好、项目固定限制、团队长期约定。

### 重要事件

例如一次关键决策、一次事故结论、一次已经验证过的失败方案。

### 可复用经验

例如某类任务中反复成立的做法或陷阱。

它们的共同点不是“出现过”，而是**未来仍可能改变决策**。

## 什么不应该轻易进入长期 Memory

- 当前任务的临时 Todo；
- 某次工具调用的原始输出；
- 尚未验证的猜测；
- 很快会过期的状态；
- 可以从权威数据源实时查询的事实。

这些信息如果被永久保存，会让 Memory 越来越像垃圾场。

## 先区分 History、State、Memory

**History**：之前说过、做过什么。  
**Task State**：这个任务现在进行到哪里。  
**Long-term Memory**：哪些过去信息值得未来任务重新取回。

三者可以互相转化，但职责不同。

例如一次对话里确认了“项目只能使用 Java 21”，它最初存在于 History；当前任务需要时会进入 State；如果这是项目长期约束，最后才值得写入 Memory。

## 地图坐标

Memory 在这一章只作为 **Source** 出现。

真正困难的“什么时候写、什么时候读、什么时候忘”，第 17 章再处理，避免把存储和生命周期混在一起。
