# 14｜Lifecycle：信息什么时候该进入，什么时候该离开

Context 最大的工程变化之一，是从“静态文本”变成有生命周期的信息。

一条信息至少可能经历：

~~~
产生
↓
进入 Context
↓
被使用
↓
写入 State / Memory
↓
压缩或降级
↓
过期
↓
删除或重新验证
~~~

## 不同信息有不同寿命

### 一轮有效

例如某次工具调用的原始返回。

### 一个任务有效

例如当前计划、临时候选假设。

### 一个会话有效

例如用户在这次讨论里设定的目标。

### 长期有效

例如稳定偏好或项目固定规则。

如果所有内容都用同一个保留策略，系统迟早混乱。

## Freshness 必须被设计

价格、库存、权限、项目状态都可能变化。

长期 Memory 或缓存里保存的内容，不能默认永远正确。

可以给信息附加：

- timestamp；
- source；
- ttl；
- version；
- confidence。

在高风险场景里，使用前重新验证比“记住”更重要。

## 删除是一种能力

很多系统只会“加 Context”，不会“减 Context”。

但能主动丢弃过期信息，和能检索新信息一样重要。

真正成熟的 Context 系统应该知道：

> 什么已经不值得继续相信，也不值得继续携带。

## 地图坐标

Lifecycle 决定 Context 在时间上的行为。

Memory、Session、Checkpoint、Cache 和 Compaction 都可以放在这里理解。
