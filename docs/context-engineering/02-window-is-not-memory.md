# 02｜Context Window 不是 Memory

上下文窗口变大以后，很容易产生一种安心感：

> 只要窗口足够大，把历史都放进去，不就等于模型什么都记得了吗？

这个直觉在短任务里看不出问题。任务一长，它就会失效。

Context Window 说的是：**一次推理最多能让模型看到多少内容。**

Memory 说的是：**哪些信息值得跨时间保存，以及以后什么时候把它重新带回来。**

两者一个是容量，一个是信息生命周期。

## 想象一个连续工作三天的 Agent

第一天，它发现某个接口存在兼容性限制。

第二天，它完成了一半改造。

第三天，它继续工作。

如果系统一直保留完整历史，那条兼容性限制当然还“在”。

但几个问题马上出现：

- 这条限制今天还成立吗？
- 它重要到值得每一轮都重新发送吗？
- 它是否已经应该从聊天记录提升为“已确认事实”？
- 如果接口升级，旧限制什么时候作废？

这些问题都不是窗口大小能回答的。

## 大窗口解决不了“信息失序”

即使还远没碰到硬上限，Context 也可能已经不好用：

- 关键事实藏在很早以前；
- 同一件事出现了多个版本；
- 已完成步骤持续占空间；
- 工具日志一轮轮累积；
- 模型每次都要重新从历史里推断当前状态。

因此，一个能装很多东西的窗口，并不等于一个好的记忆系统。

## 先把三个概念分开

**Context Window**：一次推理的容量边界。  
**Runtime Context**：这一轮模型实际看到的内容。  
**Memory**：让信息跨时间保存，并在需要时重新进入 Runtime Context 的机制。

后面谈 History、State、Memory、Compaction 时，都建立在这个区分上。

## 地图坐标

Window 主要约束 **Budget**。

Memory 则主要落在 **Source + Select + Lifecycle**。

把它们拆开以后，很多原本纠缠在一起的问题会变得清楚。
