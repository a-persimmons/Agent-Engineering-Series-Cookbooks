# 02｜Context Window 不是 Memory

上下文窗口变大以后，一个直觉很容易出现：

> 既然能放几十万甚至更多 token，是不是把历史都放进去就等于有记忆了？

不是。

Context Window 描述的是**一次推理时模型最多能看到多少内容**；Memory 描述的是**系统如何在时间上保存、选择并重新带回信息**。

两者解决的不是同一个问题。

## 一个简单例子

假设一个 Agent 连续工作三天。

第一天发现某个接口存在兼容性限制；第二天修复了一半；第三天继续任务。

如果系统只是保留完整对话历史，它当然可能把第一天那句话一直带着。

但这并不意味着记忆设计合理：

- 那条信息还有效吗？
- 它重要到值得每轮都占 Context 吗？
- 是否应该被整理进“已确认事实”而不是埋在聊天记录里？
- 如果后来限制解除，旧信息什么时候失效？

Memory 的核心是**持久化 + 检索 + 生命周期**，而不是“历史还在”。

## 大窗口也会产生信息质量问题

即使不触碰硬上限，Context 仍可能失败：

- 重要信息埋得太深；
- 同一事实出现多个版本；
- 已完成步骤仍占大量空间；
- 工具日志反复累积；
- 模型需要重新理解整个历史。

所以真正的目标不是“避免超窗”，而是维持一个对当前任务有用的工作集。

## 三个概念先分开

**Context Window**：模型一次能处理的容量边界。  
**Runtime Context**：这一轮实际送进模型的内容。  
**Memory**：让信息跨时间保存并按需重新进入 Runtime Context 的机制。

后面所有章节都会建立在这个区分上。

## 地图坐标

Window 主要影响 **Budget**；Memory 主要落在 **Source + Lifecycle**。

把这两个概念分开以后，很多设计问题会立刻清楚。
