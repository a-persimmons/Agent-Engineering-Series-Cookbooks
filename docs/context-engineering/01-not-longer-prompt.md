# 01｜Context Engineering 不是“写一个更长的 Prompt”

第一册结束时，我们已经看到一个变化：Prompt 不再只是一段手写文本。

复杂系统的一次模型调用，可能同时包含：

- 固定指令；
- 用户当前请求；
- 对话历史；
- 当前任务状态；
- 检索到的资料；
- 长期记忆；
- 工具定义；
- 工具结果；
- 环境状态。

这些内容共同组成模型此刻可见的世界。

## 关键问题已经变了

Prompt Engineering 常问：

> 这句话怎么写，模型才更容易按要求做？

Context Engineering 更关心：

> 在这一轮判断发生之前，模型应该看到哪些信息？

区别看起来很小，工程含义却很大。

当信息是静态的，你可以手工整理；当系统持续运行，Context 必须动态装配。它会随着任务阶段、工具调用和状态变化不断改变。

## “全部给它”为什么不是最稳妥的办法

把所有资料都放进窗口，看起来最保险。

但模型的注意力不是无限资源。无关历史、重复工具输出、旧计划、过期事实都会与当前真正重要的信息竞争。

于是“信息更多”可能带来：

- 重点变模糊；
- 旧状态覆盖新状态；
- 相互冲突的规则同时存在；
- 成本和延迟上升；
- 错误更难定位。

Context Engineering 的目标不是把窗口填满，而是提高**每个 token 对当前决策的价值**。

**从“Prompt 里还能加什么”切换到“这一轮到底应该看什么”。**
