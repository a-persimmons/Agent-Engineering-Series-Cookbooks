# 01｜Context Engineering 不是“写一个更长的 Prompt”

一个 AI 应用刚开始时，Context 往往很干净。

一段 System Prompt，一条用户输入，调用模型，拿到结果。

后来功能慢慢长出来：有了历史对话，有了知识库，有了工具，有了长期记忆，还有任务状态。于是最初那段清爽的输入，逐渐变成一只不断往里塞东西的行李箱。

这时最容易出现一个误解：

> Context Engineering，就是想办法把更多东西装进去。

恰恰相反。

## 问题已经从“怎么写”变成“该看什么”

Prompt Engineering 常问：

> 这句话怎么表达，模型才更容易按要求做？

Context Engineering 更关心：

> 在模型做这个决定之前，哪些信息应该出现在它眼前？

当信息是静态的，你可以手工整理；当系统持续运行，这件事就必须动态完成。

不同任务阶段，需要的 Context 会变化。一次工具调用可能带来新事实，一段旧历史可能已经没有价值，一个曾经正确的状态也可能在下一分钟失效。

Context 不再是一段文本，而是一个不断更新的工作现场。

## “全部给它”为什么反而危险

把资料全部放进去，看起来最稳妥。

但模型并不是把窗口里的每个 token 都当成同等重要的事实。无关历史、重复工具输出、旧计划和过期状态会与当前最重要的信息争夺注意力。

于是，窗口还没有装满，系统已经开始变差：

- 重点越来越模糊；
- 旧状态压过新状态；
- 冲突规则同时出现；
- 成本和延迟持续上升；
- 出错后很难解释模型当时为什么那样判断。

所以 Context Engineering 的目标不是“最大化输入”。

它要做的是另一件事：

> **让当前这一步真正有用的信息，占据当前这一步的注意力。**
