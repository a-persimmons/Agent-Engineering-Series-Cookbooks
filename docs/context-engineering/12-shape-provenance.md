# 12｜Shape：信息以什么形态进入模型

同一份信息可以有很多形态：

- 原始全文；
- 摘要；
- 表格；
- JSON；
- 事实列表；
- 时间线；
- 状态对象。

Shape 决定模型怎么消费它。

## 原文不是默认最佳形态

例如线上事故有 10 万行日志。

真正需要的可能是：

~~~text
14:02:11 支付服务超时开始
14:02:14 连接池占满
14:02:17 上游重试激增
14:05:03 服务恢复
~~~

如果任务是建立事件因果链，时间线比原始日志更适合当前步骤。

但原始日志仍应该保存在外部，便于回查证据。

## 保留 Provenance

压缩和改写 Context 时，一个风险是来源丢失。

如果模型看到“支付服务在 14:02 开始异常”，最好还能知道：

- 来自哪份日志；
- 哪一行或哪一段；
- 时间；
- 是否经过摘要；
- 是否为模型推断。

这让后续验证和纠错更容易。

## 事实、推断、计划要分开

Context 里最危险的混合之一，是把模型自己的旧推断当成事实继续传下去。

可以显式区分：

~~~text
Facts
Hypotheses
Decisions
Open Questions
Next Actions
~~~

这类结构能减少“错误一旦写进历史就不断自我强化”。

## 地图坐标

Shape 决定“选中的信息怎样被表达”。

好的 Shape 让模型少做一次无谓的整理，把注意力用在真正的判断上。
