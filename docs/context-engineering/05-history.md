# 05｜Conversation History：历史不是状态

把完整聊天记录作为上下文，是最省事的多轮方案。

也是最容易失控的方案之一。

## History 有什么价值

它能帮助模型理解：

- 用户刚刚说过什么；
- 指代关系；
- 已经讨论过哪些方案；
- 对话风格和局部偏好。

短对话里，这通常足够。

## History 为什么不能代替 Task State

假设用户正在做一个十步任务。

如果“第 3 步已完成、第 4 步失败、当前等待确认”只存在于聊天历史里，模型每一轮都要重新从大量自然语言里推断状态。

这很脆弱。

更好的做法是把任务进展提升为显式状态：

~~~json
{
  "goal": "完成迁移",
  "completed": ["schema audit", "backup"],
  "current": "data migration",
  "blocked_by": "permission approval"
}
~~~

History 保存发生过什么；State 保存**现在是什么状态**。

## 什么时候裁剪 History

可以优先丢弃：

- 已经被状态吸收的重复讨论；
- 失败但已废弃的探索分支；
- 大段工具原始输出；
- 已经有可靠摘要的旧轮次。

但不要机械按“最近 N 条”裁剪。最近不一定重要，重要也不一定最近。

## 地图坐标

History 是 **Source**，但它强依赖 **Select + Lifecycle**。

当对话越长，真正需要的不是更大的历史列表，而是更清楚的状态与保留策略。
