# 13｜Budget：Context 的稀缺资源不只是 token

谈 Context Budget 时，人们最先想到窗口上限。

但很多系统在“装不下”之前就已经开始退化：低价值历史、重复证据和工具日志不断占据模型注意力。

所以至少要同时看三种预算：

- **容量预算**：能放多少；
- **注意力预算**：关键内容是否仍然突出；
- **成本预算**：输入带来的延迟和费用。

## 先决定什么值得留下

Budget 管理的第一步不是压缩，而是 Selection。

如果一段内容已经没有当前决策价值，直接删掉通常比“把它总结短一点”更干净。

## 三种常见减负手段

### Trimming

删除低价值、重复或过期内容。

### Summarization

把较长历史改写成更短的语义表示。

适合保留大意，但要接受细节损失。

### Compaction

为后续继续工作重建一个更小的工作状态。

它不仅要“短”，还要保留下一阶段继续执行所需的信息。

这一章只区分三者。第 19 章会专门讨论长任务里的 Compaction 应该保留什么。

## 不要只监控 token 数

同样是 100K token：

- 可能大部分都是当前任务需要的代码和证据；
- 也可能 70% 是已经无用的历史日志。

长度相同，Context 质量完全不同。

更值得监控的是：

> 高价值信息在整个 Context 中占多大比例？

## 地图坐标

Budget 回答的是“有限注意力怎样分配”。

它依赖 Selection，也会反过来决定何时需要 Shape、Trimming 或 Compaction。
