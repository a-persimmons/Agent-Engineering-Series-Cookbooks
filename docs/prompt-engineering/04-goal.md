# 04｜Goal：到底要完成什么

Goal 决定了后面所有设计。如果目标本身模糊，后续 Context、Process 和 Output 写得再精致，也只是更稳定地完成一个错误任务。

## Goal 不等于“主题”

“分析日志”是主题。

“根据给定日志定位最可能导致请求超时的根因，并给出可验证的证据链与下一步排查动作”才接近目标。

一个可用的 Goal 通常包含三件事：

- **对象**：处理什么。
- **目的**：为什么处理。
- **成功条件**：做到什么程度算完成。

## 不要让“优秀、专业、详细”替代标准

这些词听起来有要求，其实没有给模型可执行的信息。

“写得专业”不如：

> 面向有 3 年 Java 经验的后端工程师；术语可以直接使用，但每个结论要有代码或日志证据。

“分析得深入”不如：

> 至少给出两个候选根因，并说明支持与反对每个候选的证据。

可执行标准越明确，模型越少依赖猜测。

## 一个 Goal 模板，但不要背模板

写任何模板之前，先回答：

1. **要解决哪个真实问题？**
2. **谁会使用结果？**
3. **使用结果之后要做什么决策或动作？**
4. **什么结果可以直接进入下一步？**

这四个问题比“你是一个世界级专家”有用得多。

## 什么时候 Goal 已经够清楚

拿掉 Prompt 里的模型字样，把任务交给一个靠谱同事。如果对方仍然会问“你到底想让我做什么”，Goal 还没写完。

## 挂回地图

Goal 负责压缩任务的自由度。

它不是为了让 Prompt 更正式，而是为了让后续每一层都有方向。下一层是 Context：为了完成这个 Goal，模型到底缺什么信息？
