# 11｜Reasoning：什么时候需要推理过程

复杂任务往往不是“知道答案”就够了，而是要经历一系列互相依赖的判断。

这时才值得讨论推理过程。

## 不要把“step by step”当成万能开关

给任何任务都加一句“请一步一步思考”，并不会自动提升质量。

真正有效的是把任务本身的结构表达出来。

例如故障分析：

~~~
现象确认
→ 时间线
→ 候选根因
→ 支持证据
→ 反证
→ 结论
→ 验证动作
~~~

这比一句泛化的“认真思考”更稳定，因为你明确了中间产物。

## CoT 解决什么问题

可以把 Chain-of-Thought 理解成：让复杂判断拥有中间计算，而不是强迫模型从输入直接跳到结论。

但在工程系统里，更应该关心的是：

- 哪些中间结果需要显式保留。
- 哪些结果需要检查。
- 哪些结果会影响下一步工具调用。
- 哪些推理无需展示给最终用户。

## 推理不等于解释

用户真正需要的是**可验证的依据**，不是模型内部所有思考。

因此，对外输出“证据链、计算过程、决策依据”通常比要求暴露完整思维过程更有价值。

## Self-Consistency、Tree of Thoughts 怎么看

不要按技巧背。

它们都在处理“单一路径不够可靠”：

- Self-Consistency：比较多个候选结果。
- Tree of Thoughts：显式探索多个分支。
- Critic / Reflection：让当前结果接受第二次检查。

选择这些方法之前，先证明单一路径确实是瓶颈。

## 挂回地图

Reasoning 属于 **Process**。

它不是 Prompt Engineering 的中心，而是 Process Design 面对复杂任务时的一组工具。
