# 17｜版本化与回归

当 Prompt 进入真实产品，它就不该再是一段散落在代码里的字符串。

它会随着模型、业务规则、测试集和失败案例一起变化。

## 为什么要版本化

假设 V7 比 V6 在十个案例上表现更好。两周后模型升级，三个老案例又失败了。

如果你不知道：

- V6 到 V7 改了什么。
- 为什么改。
- 当时解决了哪些 Case。
- 哪些指标提升。
- 哪些指标下降。

你只能重新猜。

## 每个版本至少留下四样东西

### 1. 变更原因

不要写“优化提示词”。

写：

> 修复证据不足时仍输出确定根因的问题。

### 2. 变更内容

明确是 Goal、Context、Process、Output 还是 Constraints 变化。

### 3. 关联 Case

哪些失败样本触发这次修改。

### 4. 回归结果

新问题是否解决，旧能力是否退化。

## Prompt 和模型版本要一起记录

同一个 Prompt 在不同模型上行为可能不同。

所以测试记录至少应该包含：

~~~
prompt_version
model
model_config
test_set_version
metrics
date
~~~

否则“上个月明明很好”无法被解释。

## 不要追求一个永远不变的最佳 Prompt

业务会变，模型会变，数据会变。

工程目标不是找到永恒答案，而是建立一条**可解释、可回滚、可回归**的演化链。

这也是从“会写 Prompt”走向“维护 AI 系统”的分界线。
