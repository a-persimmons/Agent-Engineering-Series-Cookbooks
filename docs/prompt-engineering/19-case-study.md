# 19｜一个 Prompt 是怎样长出来的

我们用一个开发者常见任务，把前面的地图完整走一遍。

原始需求只有一句：

> 帮我分析这段线上异常日志。

先看完整演化，再逐层拆开：

![一个 Prompt 从 V0 到 V6 的演化](/diagrams/prompt/evolution.svg)

## V0：一句话

问题很快出现：

- 有时解释异常类型，有时猜根因。
- 经常把二次异常当作第一原因。
- 给出的建议太泛。
- 没有证据绑定。

这时不要马上加技巧。先按地图定位。

## V1：先改 Goal

> 找出最可能导致本次请求失败的根因，并给出支持该判断的日志证据与下一步验证动作。

任务方向第一次稳定。

## V2：补 Context

加入：

- 服务拓扑。
- 请求时间线。
- 最近变更。
- 相关日志。
- 已知正常行为。

这一步之后，很多“幻觉”自然减少，因为模型终于拥有必要事实。

## V3：设计 Process

要求先完成四个中间产物：

1. 确认首个异常时间点。
2. 列出候选根因。
3. 为每个候选找支持与反对证据。
4. 只保留证据最充分的候选。

这样做不是为了让 Prompt 显得复杂，而是让“从日志到根因”的过程变得可检查。

## V4：定义 Output Contract

~~~json
{
  "root_cause": null,
  "confidence": 0.0,
  "evidence": [],
  "counter_evidence": [],
  "next_steps": []
}
~~~

如果无法确认，root_cause 允许为 null。

## V5：补 Constraints

- 不得引用输入中不存在的日志。
- 无法确认时必须明确标记。
- 二次异常不能直接作为根因。
- 每个结论必须关联证据。

## V6：建立 Evaluation

准备 20 个历史事故：

- 10 个正常可判断案例。
- 5 个信息不足案例。
- 5 个容易误判的边界案例。

开始统计：

- 根因命中率。
- 无证据断言率。
- 格式合法率。
- 信息不足时的正确降级率。

## 最后发生了什么

我们没有使用一个“神奇技巧”。

Prompt 是沿着地图逐层长出来的：

~~~
Goal
→ Context
→ Process
→ Output
→ Constraints
→ Evaluation
~~~

更重要的是，每次增长都有一个真实失败作为理由。

这就是工程式 Prompt 设计最应该形成的习惯：

> **不是一次写完，而是让失败推动结构生长。**
