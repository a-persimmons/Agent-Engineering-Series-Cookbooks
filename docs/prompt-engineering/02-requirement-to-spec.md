# 02｜从需求到任务规格

“把需求说清楚”听起来正确，但它不够可操作。

真正的问题是：**清楚到什么程度才算清楚？**

## 从一句常见需求开始

> 帮我做一份竞品调研。

人能理解这句话，但它不是一个完整任务。至少还有这些空白：

- 调研用于投资、产品决策还是市场宣传？
- 比较哪些竞品？
- 关注功能、价格、用户口碑还是商业模式？
- 信息截止到什么时候？
- 需要事实还是也允许判断？
- 最终交付表格、报告还是结论？

如果这些变量没有定义，模型只能替你决定。

## 需求和任务规格的区别

需求表达的是“我想要什么”。

任务规格表达的是“什么结果算完成”。

把上面的需求改写成任务规格：

> 对 A、B、C 三款产品做功能与定价调研，目标是帮助产品经理决定下一季度优先补齐的能力。只使用给定资料中的事实；无法确认的信息标记为“未知”。最终输出功能对比表、三条关键差距和一段不超过 300 字的建议。每个结论都标明证据来源。

变化不在于文字变长，而在于几个关键变量被定下来了。

## 一个实用的转换顺序

拿到需求时，不要马上写 Prompt。先把愿望逐步收敛成一个可以验收的任务：

![从需求到任务规格](/diagrams/prompt/requirement-to-spec.svg)

例如：

“帮我看下日志”
→ “我要排查线上故障”
→ “找出最可能的根因并给证据”
→ “结论可验证，且能指导下一步排查”

最后一步尤其重要。没有成功条件，就无法进入后面的 Evaluation。
