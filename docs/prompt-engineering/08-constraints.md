# 08｜Constraints：边界与规则

Goal 告诉模型要去哪里，Constraints 告诉它哪些路不能走。

没有边界时，模型经常会为了“完成任务”主动填补空白。这在人类对话里显得积极，在工程系统里却可能成为风险。

## 好的约束不是“不要犯错”

“不要幻觉”“一定要准确”几乎不可执行。

更好的约束会描述行为：

- 资料没有支持的事实，不得当作确定结论。
- 无法确认时返回“未知”，不要补全。
- 每个根因必须绑定至少一条证据。
- 不允许修改仓库，只能给出建议。
- 无法继续完成任务时停止，并说明失败原因与仍缺少的条件。

这些规则告诉模型在不确定时应该表现出什么行为。至于超时、重试次数、权限等能够由程序强制执行的边界，后面会把它们交给系统层，而不是只写在 Prompt 里。

## 约束有四类

### 范围边界

什么属于任务，什么不属于。

### 证据边界

哪些信息可以作为依据。

### 行为边界

允许做哪些动作，禁止哪些动作。

### 失败边界

无法继续时怎样退化、停止或求助。

最后一类很重要。可靠系统不是“永远成功”，而是**失败得可预期**。

## 规则冲突怎么办

当规则越来越多，冲突就会出现。此时不要继续堆文字，而要明确优先级。

例如：

1. 安全与合规优先。
2. 不虚构事实。
3. 尽量完成任务。
4. 优化表达。

这样遇到“必须给答案”与“证据不足”冲突时，系统知道该牺牲什么。

## 挂回地图

Constraints 负责缩小允许行为的空间。

后面的 Guardrails、Permission、Sandbox，都可以看成这一思想从 Prompt 层走向系统层后的工程化版本。
