# 05｜Context：模型需要知道什么

很多 Prompt 问题，本质上不是措辞问题，而是信息问题。

如果让模型分析一段公司内部业务逻辑，却不给规则、代码和运行现象，再漂亮的提示词也无法补出真实世界里不存在于上下文的信息。

## Context 的任务：减少不必要的不确定性

可以把上下文分成五类：

| 类型 | 例子 |
|---|---|
| 背景 | 产品场景、用户类型、系统架构 |
| 事实 | 文档、日志、数据库结果、政策 |
| 示例 | 正例、反例、边界例 |
| 历史 | 前几轮对话、之前的决策 |
| 状态 | 当前步骤、已完成任务、工具结果 |

它们不是越多越好。

真正的问题是：

> 为了做出下一步正确判断，模型现在必须看到什么？

## 缺 Context 和堆 Context 都会失败

缺信息时，模型会猜。

信息太多时，真正重要的约束可能被淹没，互相冲突的材料也会增加判断成本。

所以 Context Design 不是“把资料都塞进去”，而是做选择：

~~~
任务需要什么
↓
哪些信息必须出现
↓
哪些可以按需获取
↓
哪些反而应该删除
~~~

## Few-shot 为什么属于 Context

给模型两个高质量示例，本质上是在补充“任务长什么样、答案长什么样”的信息。

所以 Few-shot 不是一个独立魔法。它只是 Context 的一种形式。

如果任务规则已经非常明确，示例可能没有必要；如果“好答案”很难用文字描述，一个好示例可能比十条规则都有效。

## 一个判断题

当输出不好时，先问：

> 模型是不知道该怎么做，还是根本不知道完成任务所需的事实？

前者更像 Process 或 Instruction 问题，后者首先应该解决 Context。

## 挂回地图

Context 负责给模型一个足够但不过载的“当前世界”。

到了后面的 Context Engineering，这个问题会成为主角：不是 Prompt 里写什么，而是每一轮应该装载什么。
