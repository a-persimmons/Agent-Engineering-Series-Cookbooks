# 01｜你不是在和 AI 聊天

## 一个很容易误导人的界面

大模型最常见的入口是一只聊天框。于是我们很自然地把它理解成“一个很聪明的人”：我把事情说清楚，它就应该懂。

这种直觉在简单任务里很好用。一旦任务复杂，它会迅速失效。

因为你真正控制的并不是“一个人的理解”，而是**一次模型运行时所接收到的条件**。

可以把一次调用粗略写成：

~~~
模型行为 = 模型能力 × 当前输入条件
~~~

模型能力暂时不变时，工程上真正能控制的是后半部分：目标、信息、示例、规则、输出约定，以及这一轮之前发生过什么。

## 从“说一句话”换成“设计运行条件”

假设你写：

> 帮我分析这个 Java 异常。

这句话没有错。但它留下了大量未定义空间：

- 你要的是根因，还是异常解释？
- 需要给证据吗？
- 能不能提出推测？
- 要不要给下一步排查动作？
- 哪些日志最重要？
- 输出给开发者还是给业务方？

模型会自己补这些空白。补得恰好时，你觉得模型很聪明；补错时，你觉得它“不稳定”。

Prompt Engineering 的第一步，就是减少不必要的猜测空间。

## 一个更准确的心智模型

把 Prompt 看成“临时程序”比看成“聊天话术”更合适。

程序至少要回答：

1. 输入是什么。
2. 要完成什么。
3. 处理时遵守什么规则。
4. 最终返回什么。
5. 怎样算成功。

自然语言只是表达这些东西的载体。

**从“怎么把话说漂亮”切换到“怎么设计模型的运行条件”。**
