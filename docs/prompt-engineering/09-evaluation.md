# 09｜Evaluation：怎样知道它真的好

如果只能凭“这次看起来不错”判断 Prompt，你做的是调参，不是工程。

Prompt Engineering 真正进入工程阶段的标志，是开始维护**测试案例和失败记录**。

## 先别追求一个总分

不同任务的“好”不同。

根因分析可以看：

- 根因是否正确。
- 是否引用真实证据。
- 是否把猜测标成猜测。
- 是否给出可执行的验证动作。

结构化抽取可以看：

- 字段准确率。
- 格式合法率。
- 漏字段率。
- 多余字段率。

写作任务则可能看：

- 信息完整性。
- 目标读者适配。
- 事实一致性。
- 编辑质量。

## 最小评测集

刚开始不需要一百条。

先准备三类：

1. **正常案例**：最常见输入。
2. **边界案例**：信息少、输入长、格式异常。
3. **失败案例**：历史上真的出过问题的样本。

十到二十条高质量样本，往往比不断手改 Prompt 更有价值。

## 每次修改都回答一个问题

不要写“优化 Prompt”。

应该写：

> V3：降低证据不足时强行下结论的问题。

然后让评测告诉你：

- 这个问题是否变少。
- 原本正常的案例有没有变坏。

这就是回归。

## LLM-as-Judge 不是自动真理

模型可以帮助评分，但评判标准仍要由你定义。没有清晰 Rubric，只是把“感觉”外包给另一个模型。

## 挂回地图

Evaluation 让前五层第一次形成闭环：

~~~
设计 → 运行 → 评价 → 发现失败 → 定位层级 → 修改
~~~

从这里开始，Prompt 不再是一次性文案，而是可迭代的软件资产。
