# 12｜Decomposition：复杂任务为什么要拆

一个任务越长，模型需要同时维持的目标、约束和中间状态越多。

“帮我研究市场、比较竞品、找到机会、给出方案、再写成 PPT”听起来像一件事，实际上包含多个性质不同的子任务。

## 拆分的价值不是“显得有步骤”

拆分主要解决三件事：

1. 每一步需要的 Context 不同。
2. 每一步可以单独验证。
3. 失败后只重做局部，而不是全部重来。

例如：

~~~
问题定义
↓
信息收集
↓
事实整理
↓
比较分析
↓
机会判断
↓
报告生成
~~~

“信息收集”和“机会判断”需要的工具、上下文和评价方法完全不同。

## 按产物拆，而不是按动词拆

“先分析，再思考，再总结”几乎没有提供结构。

更好的方式，是让每一步产生明确产物：

- 竞品功能矩阵。
- 用户抱怨主题列表。
- 未满足需求候选。
- 证据与置信度。
- 最终建议。

产物可以检查，也可以成为下一步的 Context。

## 什么时候不该继续塞进一个 Prompt

当你发现：

- 中间状态需要长期保存。
- 不同步骤需要不同工具。
- 某一步失败后需要重试。
- 流程存在分支。
- 任务跨越多轮甚至数小时。

这已经开始离开单次 Prompt，进入 Workflow 或 Agent 的范围。

## 挂回地图

Decomposition 从 **Process** 出发，却会自然碰到 **State、Tool、Loop**。

这就是 Prompt Engineering 与 Agent Engineering 第一次真正接壤的地方。
