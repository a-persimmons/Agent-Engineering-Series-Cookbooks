# 07｜Output：定义交付合同

很多 Prompt 的失败并不是“答案错”，而是“答案没法直接用”。

对人阅读的报告、给程序消费的 JSON、给主管看的结论，哪怕内容来源相同，输出设计也完全不同。

## Output Contract 是什么

把输出看成一份交付合同，至少定义：

- 内容必须包含什么。
- 内容可以不包含什么。
- 结构是什么。
- 字段分别表示什么。
- 长度与粒度如何。
- 失败时怎样表达。

例如：

~~~json
{
  "root_cause": "string | null",
  "evidence": ["string"],
  "confidence": 0.0,
  "next_steps": ["string"]
}
~~~

这个结构比“请用 JSON 输出”强得多，因为它定义了语义。

## 格式和语义不是一回事

JSON 只保证形状，不保证内容正确。

即使 Schema 完全合法，也可能出现：

- evidence 里放的是猜测。
- confidence 永远写 0.9。
- root_cause 没有证据支撑。

所以 Output Contract 还要与 Constraints 和 Evaluation 联动。

## 面向人的输出也应该有合同

例如：

> 先给一句结论；再给三条证据；最后给下一步动作。不要复述原始材料。

这同样是结构化输出，只是不要求机器格式。

## 挂回地图

Output 决定“完成后的东西长什么样”。

如果结果要进入数据库、接口或自动化流程，输出合同应尽量机器可验证；如果给人决策，则优先保证信息层次与可读性。
