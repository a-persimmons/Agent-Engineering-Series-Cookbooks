# 15｜Prompt Debugging

真正拉开差距的，不是“第一次写得多好”，而是结果不对时能不能迅速定位。

![Prompt Debugging 诊断树](/diagrams/prompt/debug-tree.svg)

## 不要从措辞开始改

假设模型输出了一段没有证据的根因结论。

低效做法：

> 请更严谨一些，一定要基于证据。

更好的调试方式：

1. Goal 是否要求“给证据”？
2. Context 中是否真的存在证据？
3. Process 是否要求先找证据再下结论？
4. Output 是否为 evidence 留了明确位置？
5. Constraints 是否禁止无证据断言？
6. Evaluation 是否能识别“结论无证据”？

一次失败可以穿过整张地图检查。

## 一次只改一个主要变量

如果同时改 Goal、换模型、增加示例、重写格式，你最后不知道是什么起了作用。

工程调试更像控制实验：

~~~
V1：基线
V2：只增加证据约束
V3：在 V2 上增加边界示例
V4：在 V3 上调整输出合同
~~~

每一次修改都应该有理由。

## 建一个失败日志

至少记录：

| 字段 | 含义 |
|---|---|
| Case | 输入样本 |
| Expected | 预期结果 |
| Actual | 实际结果 |
| Failure Type | 失败类型 |
| Hypothesis | 可能原因 |
| Change | 本次修改 |
| Result | 是否改善 |

积累一段时间后，你会发现最有价值的资产并不是“最终 Prompt”，而是**为什么它变成今天这样**。

## 调试顺序

固定顺序的意义，不是每次机械检查六遍，而是先根据失败表现找到最可能的责任层，再向前追根因。

例如“没有证据却下了确定结论”，表面看是 Constraints 失效，但继续往前追，可能发现 Context 根本没有足够证据。真正要修的是**第一次发生不可接受偏差的位置**。

这能减少凭感觉乱改，也能避免在下游用更长的规则掩盖上游缺陷。
