# 03｜模型为什么会答坏

模型回答不好时，人最容易做两件事：重新措辞，或者再强调一次“请认真”。

这两种办法偶尔有效，但很难复用。更有用的做法，是先判断失败来自哪里。

## 六类常见根因

### 1. 目标问题

模型完成了一个“合理任务”，但不是你真正想要的任务。

典型症状：答案看起来不错，却没法拿去用。

### 2. 信息问题

模型缺少完成任务所需的事实，只能依赖已有知识或猜测。

典型症状：细节似是而非、年份错、业务规则被补写。

### 3. 过程问题

任务本身包含多个依赖步骤，却被要求一步给出最终答案。

典型症状：复杂分析跳步、前后矛盾、漏掉关键分支。

### 4. 输出问题

内容大体正确，但形状不适合后续消费。

典型症状：该给 JSON 时夹带解释，该给结论时写成长文。

### 5. 边界问题

允许和禁止的行为没有被定义。

典型症状：证据不足时仍然下结论，超出资料范围自由发挥。

### 6. 评价问题

你其实没有定义“好”的标准。

典型症状：Prompt 越改越长，却不知道哪个版本更好。

## 不要把所有失败都叫“幻觉”

“幻觉”是一个结果描述，不是足够精确的工程诊断。

如果缺资料，应该补 Context；如果证据不足仍强行作答，应该补 Constraints；如果结论没有依据，可能还需要改变 Output Contract，让每个结论必须绑定证据。

同一个表面问题，可以来自完全不同的根因。

## 从现在开始，先分类再修改

以后看到失败，先暂停“改措辞”的冲动。先描述失败表现，再用六问地图定位最可能的责任层：

~~~
Goal 对吗？
Context 够吗？
Process 合适吗？
Output 清楚吗？
Constraints 有漏洞吗？
Evaluation 能发现问题吗？
~~~

这不是要求每次从头到尾机械检查一遍，而是给失败一个共同坐标系：先定位，再修改。
