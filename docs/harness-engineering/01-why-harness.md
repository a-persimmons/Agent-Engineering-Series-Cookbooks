# 01｜为什么“能跑”还远远不够

Agent 最容易让人兴奋的时刻，是它第一次真的把事情做成。

模型会查资料，会改文件，会跑测试，会根据结果继续下一步。看起来已经不再只是聊天，而像一个真正的执行者。

问题往往从第二次、第三次、第一百次运行才开始出现。

某次 Shell 卡住了。

某次 Tool 已经成功，程序却因为超时又执行了一遍。

某次 Agent 修改了工作区之外的文件。

某次任务跑到一半进程重启，回来以后不知道自己做到哪里。

这时才会发现：

> “能跑通一次”与“能长期被信任”之间，还隔着一整层工程。

## Demo 隐藏了很多幸运条件

最小 Agent 往往默认：

- Tool 会正常返回；
- 环境不会变化；
- 文件不会冲突；
- 模型会自己停止；
- 权限天然正确；
- 进程不会中断；
- Action 失败不会留下半完成副作用。

这些假设在 Demo 里通常成立。

在真实系统里，它们迟早会被打破。

## Harness 管的不是“怎么想”，而是“怎么运行”

Agent Loop 可能决定：

> 删除这个临时文件。

Harness 需要继续问：

~~~text
这个文件在允许范围内吗？
↓
当前任务有写权限吗？
↓
是否需要审批？
↓
动作最多执行多久？
↓
执行结果如何记录？
↓
中断以后是否会重复执行？
~~~

真正的生产执行，不应该只有中间那一步 delete。

## Harness 不等于某个框架

某个 Agent SDK 可以提供一部分 Harness 能力。

某个 Coding Agent 也会自带自己的 Harness。

但 Harness Engineering 更底层。

即使完全自己写 Runtime，你仍然绕不开：

- Permission；
- Sandbox；
- Timeout；
- Retry；
- Persistence；
- Trace；
- Recovery。

## 地图坐标

Agent 负责决定下一步做什么。

Harness 负责让这一步在一个**有边界、有记录、有恢复路径**的环境里发生。
