# 03｜Workflow 还是 Agent

“这个需求要不要做 Agent？”

先别看技术栈，也别看最近流行什么框架。

只问一个问题：

> **下一步动作，能不能在运行之前基本确定？**

这个问题往往已经能把大部分场景分开。

## 能提前写清楚的，先做 Workflow

例如发票处理：

~~~text
OCR
↓
字段抽取
↓
规则校验
↓
入库
~~~

步骤、顺序和失败路径都比较明确。

模型当然可以参与 OCR 后的抽取和判断，但整个控制流不需要由模型决定。

这种系统的优势很直接：

- 容易测试；
- 容易复现；
- 成本可控；
- 出错位置清楚。

## 路径必须边走边决定，才开始需要 Agent

再看线上故障排查。

你很难事先知道：

- 先查数据库还是网关；
- 看完第一组日志之后要不要查 trace；
- 当前假设被否定以后下一步去哪。

这里的中间结果会改变后面的路径。

于是控制流的一部分必须在运行时决定。

这才是 Agent 真正有价值的地方。

## Agent 不是 Workflow 的升级版

自主性更高，不代表架构更高级。

它只是把更多控制权交给模型，同时接受新的成本：

- 行为更难预测；
- 测试空间更大；
- 失败路径更多；
- 安全边界更难设计。

能用 Workflow 解决的问题，硬做成 Agent，通常只是增加不确定性。

## 地图坐标

Workflow 把 **Loop** 提前写好。

Agent 把一部分 **Decision** 留到运行时。

后面的架构设计，本质上都在回答同一个问题：

> 控制权到底应该留在程序里，还是交给模型？
