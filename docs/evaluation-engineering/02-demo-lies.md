# 02｜为什么一个漂亮 Demo 很容易骗过我们

AI Demo 往往很有说服力。

输入一个问题，模型迅速完成分析；Agent 自动调用几个工具，最后给出漂亮结果。

看三五次以后，很容易产生一种判断：

> 这个方案已经差不多了。

问题在于，Demo 天然处在一个“被照顾过的世界”里。

开发者会下意识挑那些：

- 信息比较完整；
- 表达比较清楚；
- 工具能够正常返回；
- 不涉及太多边界；
- 自己大概知道正确答案；

的例子。

而真实用户不会替系统挑题。

## 生产环境专门会送来那些“难看的输入”

例如：

- 只说半句话；
- 一次问三个问题；
- 给出互相冲突的资料；
- 引用已经过期的规则；
- Tool 正好超时；
- 任务跑到一半进程重启；
- 请求碰到权限边界；
- 输入比你测试过的长十倍。

这些情况往往不是 Demo 的重点，却是系统真正决定能不能用的地方。

## 模型还有另一个麻烦：一次成功不代表稳定成功

同一个输入，这次答得很好。

下一次可能就少了一条证据。

所以一张“成功截图”最多证明：

> 它曾经成功过一次。

它证明不了成功率，更证明不了边界。

## Eval 的视角正好相反

Demo 问：

> 它能做到什么？

Evaluation 更关心：

> **它在什么条件下会做不到？**

这个变化很重要。

因为工程系统真正需要知道的，不只是能力上限，而是失败边界。

Cases 的作用，就是把这些边界从偶然撞见，变成主动测试。
